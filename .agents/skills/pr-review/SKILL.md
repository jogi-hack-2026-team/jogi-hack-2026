# Pull Requestレビュー

このSkillは、自分自身の変更ではなく、他メンバーが作成したPull Requestをレビューするときに使用する。

レビューの目的は、単にコード上の問題を探すことではない。

以下を確認する。

- Issueで求められていることを満たしているか
- 実装が正しく動作するか
- 不要な変更が含まれていないか
- 将来的に理解・変更しやすいか
- プロジェクトで採用している設計と矛盾していないか
- 必要なテストが存在するか
- ドキュメントとコードが一致しているか

レビューでは、個人的な好みと修正必須事項を区別する。

---

# 1. プロジェクトルールを確認する

最初に以下を読む。

1. `AGENTS.md`
2. `CONTRIBUTING.md`
3. 必要に応じて `docs/DEVELOPMENT_GUIDE.md`
4. 必要に応じて `docs/architecture/`
5. 必要に応じて `docs/decisions/`

リポジトリで既に決定されているルールを優先する。

レビュー時に独自の設計ルールやコーディング規約を追加しない。

---

# 2. Pull Requestの前提を確認する

[採択済み方針](../../../AI_DEVELOPMENT_TOOLS.md#採択済みの運用方針)に従い、基本はGitHub CLIで対象Pull Requestを確認する。
未導入・認証不可などで利用できない場合はGitHub Web UIで代替する。

例:

```bash
gh pr view <PR番号>
```

必要に応じて変更内容を確認する。

```bash
gh pr diff <PR番号>
```

以下を確認する。

- 関連Issue
- PRの目的
- 変更内容
- 完了条件
- テスト方法
- 補足事項

関連Issueがある場合は必ずIssueも確認する。

```bash
gh issue view <Issue番号>
```

IssueとPRの内容が一致していない場合は、その点をレビュー対象とする。

---

# 3. まず変更全体を理解する

コードの細かい指摘を始める前に、PR全体として何を変更しているのか理解する。

確認する。

- 何を解決するPRなのか
- どのファイルが変更されたか
- どの責務が変更されたか
- 新しい依存関係が追加されたか
- データ構造が変わったか
- APIや外部I/Oが変わったか
- ユーザー向け挙動が変わったか

必要に応じてSerenaを使用して以下を調査する。

- symbolの定義
- 呼び出し元
- 呼び出し先
- 参照関係
- 変更による影響範囲

変更されたコードだけを見て判断せず、必要な周辺コードも確認する。

---

# 4. Issueとの整合性を確認する

以下を確認する。

- Issueの目的を満たしているか
- Acceptance Criteria（完了条件）を満たしているか
- Issueで要求されていない変更が含まれていないか
- 実装によって別の仕様を勝手に追加していないか
- 未確定だった仕様を実装者が独自判断で確定していないか

Issue自体に不足や矛盾がある場合は、コードだけを問題にせず、その点を明示する。

---

# 5. 正しさを確認する

コードが期待通り動くか確認する。

特に以下を見る。

## 正常系

- 通常の入力で期待通り動作するか

## 異常系

- 不正な入力
- API失敗
- DB失敗
- 認証失敗
- データ不存在
- 外部サービス失敗

などが適切に扱われているか。

## 境界値

例:

- 0件
- 1件
- 最大値
- 空文字
- null
- undefined
- 重複値

必要なケースを確認する。

---

# 6. データと不変条件を確認する

以下を確認する。

- 不正な状態を作れるようになっていないか
- バリデーションが適切な責務に存在するか
- DB制約とアプリケーション側制約が矛盾していないか
- データ更新途中で不整合が発生しないか
- トランザクションが必要ではないか

ドメイン上の重要なルールが存在する場合は、その不変条件が維持されているか確認する。

---

# 7. 責務と設計を確認する

特定のアーキテクチャを機械的に強制しない。

現在のプロジェクトで採用されている設計に対して確認する。

見るポイント:

- 1つの関数やクラスに責務が集中しすぎていないか
- UI層にビジネスルールが漏れていないか
- Infrastructure固有処理が不自然な場所に漏れていないか
- 同じロジックが複数箇所に重複していないか
- 不必要な抽象化を増やしていないか
- 将来的な可能性だけを理由に過剰設計していないか

「より綺麗にできる」だけではBlockingにしない。

現在の変更に実害があるかを基準に判断する。

---

# 8. 型を確認する

TypeScriptを使用している場合は特に以下を確認する。

- 不要な `any`
- 強引な型アサーション
- `as`によって実行時エラーを隠していないか
- null / undefinedを正しく扱っているか
- APIレスポンスを信用しすぎていないか
- 型と実データが一致しているか

型が通ることと実行時に安全であることを混同しない。

---

# 9. エラーハンドリングを確認する

以下を見る。

- エラーを握りつぶしていないか
- ユーザーに内部情報を露出していないか
- ログへ必要な情報が残るか
- 同じエラーを二重処理していないか
- catchしただけで正常終了扱いしていないか

エラー処理を増やしすぎて本来の原因を隠していないかも確認する。

---

# 10. セキュリティを確認する

変更内容に応じて以下を確認する。

- 認証
- 認可
- 権限チェック
- 入力検証
- SQL Injection
- XSS
- CSRF
- Secretの露出
- クライアントへ送ってはいけない情報
- Server / Client境界
- ファイルアップロード
- URLや外部入力の扱い

セキュリティに関係しないPRで、機械的に全項目を問題視しない。

---

# 11. パフォーマンスを確認する

変更内容に応じて確認する。

- 不要なループ
- 不要なDB Query
- N+1 Query
- 大量データの全件取得
- 不必要な再レンダリング
- 重い処理の同期実行
- 不要なネットワークリクエスト

ただし、実際に問題にならない規模で過剰最適化を要求しない。

---

# 12. テストを確認する

以下を確認する。

- 必要なテストが追加されているか
- 正常系だけになっていないか
- バグ修正の場合、Regression Testがあるか
- 実装詳細ではなく振る舞いを確認しているか
- テストが本当に失敗条件を検出できるか

既存テストがある場合は実行する。

プロジェクトで定義されている以下を必要に応じて実行する。

- formatter
- lint
- typecheck
- unit test
- integration test

---

# 13. UI変更を確認する

UI変更がある場合は、コードだけでレビューを完了しない。

[採択済み方針](../../../AI_DEVELOPMENT_TOOLS.md#採択済みの運用方針)に従い、Playwright CLI＋Skillを使って必要な実ブラウザ検証を行う。
導入・設定が整っておらず確認できない場合は、未検証の範囲と理由を明記する。

確認する。

- 正常操作
- Empty State
- Loading State
- Error State
- レスポンシブ表示
- 操作不能な状態がないか
- 明らかなレイアウト崩れ
- キーボード操作
- アクセシビリティ上の明らかな問題

スクリーンショットだけで判断できない挙動は実際に操作する。

---

# 14. ライブラリ仕様を推測しない

フレームワークやライブラリの挙動がレビュー判断に関係する場合、記憶だけで断定しない。

必要に応じてContext7で現在の公式ドキュメントを確認する。

特に以下は確認を優先する。

- 非推奨API
- Version依存の仕様
- Security関連
- Framework固有の挙動
- Configuration

---

# 15. ドキュメントを確認する

変更によって以下が古くなっていないか確認する。

- `README.md`
- `CONTRIBUTING.md`
- `docs/DEVELOPMENT_GUIDE.md`
- `docs/product/`
- `docs/architecture/`
- `docs/decisions/`

以下に該当する場合はドキュメント更新を確認する。

- ユーザー向け挙動変更
- セットアップ変更
- 環境変数変更
- API変更
- DB変更
- アーキテクチャ変更
- 開発フロー変更
- 重要な技術判断

重要な設計判断が追加された場合はADRが必要か確認する。

---

# 16. コメントの重要度を分類する

レビューコメントは以下の3種類に分類する。

## Blocking

Merge前に修正が必要。

例:

- 仕様を満たしていない
- 明確なバグ
- データ破壊
- Security問題
- 重要なテスト不足
- 既存機能を壊す
- ドキュメントが事実と矛盾する

## Should Fix

Merge前に修正することが望ましい。

例:

- 保守性が大きく下がる
- エラー処理不足
- 命名により意図が分かりにくい
- テストケース不足
- 明確な重複処理

ただし、必ずしもMergeを止める必要はない。

## Optional

改善提案。

例:

- より読みやすい書き方
- 小規模なリファクタ案
- 将来的な改善
- 個人的な好みに近い提案

OptionalをBlockingとして扱わない。

---

# 17. レビューコメントの書き方

指摘するときは、可能な限り以下を含める。

1. 何が問題か
2. なぜ問題か
3. どのようなケースで問題になるか
4. 必要なら修正方向

悪い例:

```text
ここ違うと思います。
```

良い例:

```text
Blocking:

`user` が存在しない場合でも `user.id` を参照する可能性があります。

この状態だと未ログイン時にRuntime Errorになるため、
`user` の存在確認後に処理する必要があります。
```

実装方法が複数ある場合、1つの方法を絶対解として押し付けない。

---

# 18. 質問と指摘を区別する

意図が分からない場合は、問題と断定せず質問する。

例:

```text
Question:

ここでキャッシュを無効化しているのは、
更新直後に最新データを保証する目的でしょうか？
```

背景を理解していない状態でBlockingにしない。

---

# 19. 個人的な好みをレビュー基準にしない

以下のようなものを、根拠なく修正要求しない。

- 自分なら別の書き方をする
- 自分なら別ライブラリを使う
- 自分なら別アーキテクチャにする
- 少し短く書ける

レビューでは、

「このコードが好きか」

ではなく、

「このプロジェクトにとって問題があるか」

を判断する。

---

# 20. 過剰なスコープ拡大を要求しない

今回のIssueに含まれない大きな改善をレビューで要求しない。

別対応が必要な場合は、

- Follow-up Issue
- 将来改善
- Optional

として分離する。

「ついでに全部直してください」を避ける。

---

# 21. レビュー結果

最後に以下の形式でまとめる。

## Review Summary

PRが何を変更するものか簡潔に説明する。

## Blocking

Merge前に修正が必要な問題。

存在しない場合は「なし」と明記する。

## Should Fix

修正を推奨する問題。

存在しない場合は「なし」と明記する。

## Optional

任意の改善案。

存在しない場合は「なし」と明記する。

## Verification

確認した内容。

例:

- Issue確認
- diff確認
- typecheck
- test
- Playwright
- Context7
- Serena

## Documentation

ドキュメントへの影響と確認結果。

## Questions

実装者に確認したい点。

## Remaining Risks

レビュー時点で確認できなかった点や残っているリスク。

---

# 22. GitHubへレビューを書く場合

ユーザーからGitHub上へのレビュー投稿まで依頼された場合のみ実行する。

レビュー内容を確認したうえで、

- Comment
- Approve
- Request Changes

のどれが適切か判断する。

ただし、AIだけの判断でApproveやRequest Changesを送信しない。

最終的なレビュー状態の送信はユーザーの明示的な指示に従う。

コード上の問題を見つけた場合でも、ユーザーの確認なしにPRのコードを直接変更しない。
