# バグ調査

コードをすぐに変更しない。
調査の入口で[documentation-syncの変更前確認](../documentation-sync/SKILL.md#変更前)を読み、関連仕様・変更対応表から期待挙動と実装を照合する。現在の不具合を正式な仕様として文書化しない。

以下の順番で調査する。

1. 問題を再現する。
2. 期待される挙動を整理する。
3. 実際の挙動を整理する。
4. 最小の再現条件を特定する。
5. 関連するコードを探す。
6. 必要に応じてSerenaでsymbolやreferenceを調査する。
7. 原因仮説を立てる。
8. 仮説を証拠で検証する。
9. Root Cause（根本原因）を特定する。
10. 必要最小限の修正を行う。
11. 可能であればRegression Test（再発防止テスト）を追加する。
12. 関連テストを実行する。
13. 元の再現手順でもう一度確認する。
14. ブラウザ上の問題であれば、[採択済み方針](../../../AI_DEVELOPMENT_TOOLS.md#採択済みの運用方針)に従ってPlaywright CLI＋Skillで確認する。未導入の場合は未検証の理由を明記する。

ライブラリやフレームワークの仕様が原因候補の場合、推測せずContext7で現在の公式仕様を確認する。
修正後は同Skillの[完了前確認](../documentation-sync/SKILL.md#完了前)を行い、影響する仕様・対応表・参照を更新する。更新不要の場合は理由を報告する。

最後に以下を整理する。

- 症状
- 根本原因
- 修正内容
- 検証内容
- 残っているリスク
