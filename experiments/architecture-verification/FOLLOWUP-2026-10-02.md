## 認証、所有権、Cookie

登録→Cookieのみで再要求→session確認→logout→旧 Cookie 再利用401→再login、期限切れ401を両版で確認。未認証の保護 route は401。別 user の Goal read/today/log write/delete は404、他人の一覧へ非表示、他人のデータに副作用なしを確認した。

HTTP Cookie は HttpOnly、SameSite=Lax、Path=/、Max-Age=604800。HTTPS **base URL 設定**では Secure / `__Secure-` を確認したが、transport はローカル HTTP。公開 HTTPS・Cloud Run proxy の証拠ではない。直接 handler と Fastify の2 bridge で logout の複数 Set-Cookie 行を比較し、欠落しないことを確認した。

空 DB の auth→app migration、2回目 no-op、FK cascade/rollback、DB 制約、厳格 Ajv、serialization を再実行した。空 DB の migration 前の schema mismatch 診断が出る場合がある。これは migration 後の実 flow 成功と分けて読む。

## Origin と SameSite は別の検証

修正前は auth POST が別 Origin を403にする一方、Goal POST は Cookie＋別 Origin を201で受理した。候補修正版は auth の既存検査を保持し、アプリの状態変更 API に完全一致 Origin を要求する。POST/PUT/DELETE の cross-site、same-site別 port、`null`、欠落、偽装 suffix を403にし、Goal/log に副作用なしを確認。正常 Origin の作成・書込・削除は成功、他 user は正常 Origin でも404、Cookie＋Originなしの安全な GET は成功した。**PATCH は PoC 未実装で未検証**。Origin 欠落等の正式方針はチーム合意が必要。

既存 Chrome 154.0.8037.95 を新規の隔離 profile で使用し、同一 Origin の login/JSON書込、Cookie属性、別 Origin の JSON/fetch/form を9項目確認。JSON は OPTIONS404 と CORS preflight 拒否により実 POST はサーバーへ到着しない。simple text/form は same-site 別 port で Cookie が送付されても403、cross-site では SameSite=Lax による Cookie 非送付と403を確認した。SameSite は site に対する送付制御、Origin は scheme/host/port の検査である。これは HTTP の IP/port 条件だけで、HTTPS/subdomain・Firefox/Safari・全攻撃・ブラウザの null/missing Origin を網羅しない。

## Rate-limit と int8 の修正範囲

PG保存、ローカル trusted proxy 1 hop の bridge で、5回401→429、別 IP の独立、偽装左端 X-Forwarded-For で回避不可、実 process 再起動後429、2 process の3＋3で6回目429を確認。20並列を2 process へ送る試験は5処理/15拒否。追加10バケツ×20並列も各5/15。整数 X-Retry-After 1〜60、境界前429・経過後両 process401。小規模試験であり全競合条件や Cloud Run header 信頼は保証しない。memory storage は再起動で消え、2 process で共有しない危険を再現した。

既定 pg int8 文字列では `lastRequest + window` が連結になり、約10^14秒の待ち時間を両版で再現。1.7.7更新だけでは直らない。候補は **auth 専用 pool の text OID20だけ**を数値へ変換し、安全整数 `[-9007199254740991,9007199254740991]` 以外は RangeError。app pool は既定の文字列のまま、他 OID と global parser は変更しない。正負の安全境界・境界外・PG int8極値・他型を DB query で確認した。auth pool の全 text int8 に効くため lastRequest だけに限った変更ではない。binary int8 は未検証で既定 parser を保持する。

auth/app が独立するので通常 max5＋2＝7接続/instance、2 instance なら14。最小 staging 案の app2＋auth2 でも計8接続/2 instance。Neon の接続上限・pooled/direct URL・transaction poolingとの適合は別途確認する。429 の header と画面の待機再試行、共有回線の正当ユーザーを止めない上限は #75/#84 で合意する。
