## 1. 結論

**条件付きで採用可能。**

ローカルで確認できる範囲では、第一候補の構成は認証・DB・契約・1プロセス配信のすべてが動いた。一方で、採択前に知っておくべき落とし穴が複数見つかり、配備先での確認と予測エンジンの性能は未実施である。

| 区分 | 内容 |
| --- | --- |
| 確認できた | 登録→ログイン→再読み込み→ログアウト。未認証は401、他人のGoalは404。DB保存のレート制限が再起動と複数instanceをまたいで効き、F-10の対処後は429の待ち時間が1〜60秒の整数で返る。空DBからのmigrationが再現する。1プロセスでSPAとAPIを同一originから配信できる。SIGTERMで処理中のリクエストを完了してから終了する |
| 見つかった問題（対処を確認済み） | Fastifyの既定設定は契約違反の入力を黙って受理する。Better Auth公式ガイドの変換routeは、転送ヘッダーが複数値のとき全クライアントが1つのレート制限バケツを共有する。DB接続が既定設定のままだと、429の待ち時間ヘッダーが異常値になる。同期の計算はAPI全体を止める |
| 未実施 | 予測エンジンの単体性能（#73 T-14）。コンテナのビルド。Cloud Run ＋ Neonでの動作、休止後の応答、転送ヘッダーの実形式。費用の実測 |

**採択の条件（提案）**

1. 実装時に「厳格な入力検証設定」「修正版の変換route」「DB保存のレート制限」「`int8` を数値で読むDB接続設定（F-10）」を採用条件として#75・#76・#77へ反映する。
2. stagingの作成が承認されたら、§3.3の未実施項目を#70・#75の中で確認する。
3. 予測エンジンの実装後にT-14を計測し、結果に応じて同一プロセス内のworker poolで実行する。
4. NeonのリージョンとCloud Runのリージョンの組を、プロジェクト作成前に決める。Neonに東京リージョンはない。

**見つかった問題と対処**

| # | 問題 | 確認した事実 | 対処（確認済み） |
| --- | --- | --- | --- |
| F-1 | Fastifyの既定のAjv設定は契約違反を黙って受理する | 既定設定では「SKIPPEDにamount付き」が200、「amountが文字列」が200、「未定義の項目つきGoal作成」が201になった。未定義の項目を捨て、型を変換してから検証するため | `removeAdditional: false`、`coerceTypes: false` にすると4ケースすべて422 |
| F-2 | 422の項目別表示には全エラーの収集が必要 | 既定では最初の1件しか返らない | `allErrors: true` と、項目名を含むpathへの整形で、違反した項目がすべて返る |
| F-3 | Fastifyの検証エラーは既定で400 | 契約は422 | error handlerで422と共通のerror形式へ変換 |
| F-4 | Type Providerはpluginスコープごとに再適用が必要 | 保護plugin内でbodyやparamsの型が `unknown` になり、型検査で検出 | plugin内で `withTypeProvider` を呼ぶ |
| F-5 | 公式ガイドの変換routeは、転送ヘッダーが複数値または無いとき、全クライアントが1つのバケツを共有する | クライアントAが上限を使い切ると、別のクライアントBとヘッダーなしのクライアントも429になった。DBのキーは `no-trusted-ip\|/sign-in/email` | Fastifyの `trustProxy` で決めたIPを1つだけ専用ヘッダーで渡す修正版では、偽装した左端の値を変えても制限を回避できず、他のIPにも影響しない |
| F-6 | 認証エンドポイント全体の既定上限は1IPあたり60秒で100回で、セッション確認も対象 | 負荷試験中にセッション確認が429になった | 同じ回線から多人数が使う場面（デモ会場など）を想定して上限を設計する |
| F-7 | 制限中は正しいパスワードでも429 | 確認済み | 画面の文言で待ち時間を伝える。待ち時間を `X-Retry-After` から取る場合はF-10の対処が前提 |
| F-8 | アプリのrouteはOriginを検査しない | 外部OriginとCookieを付けたPOSTが201になった（ブラウザ以外のクライアントで再現）。この試験が示すのは、アプリrouteにOrigin検査がないことまでである。`SameSite=Lax` がCookieを止めるのは、cross-site（schemeまたはeTLD+1が異なる）からのPOSTや埋め込みの要求で、別subdomainや別portのようなsame-siteの別originからの要求にはCookieが付く。実ブラウザでのCSRFの確認は未実施 | **未対処。** 状態を変えるrouteのCSRF／Origin検査の方針を#75・#76で決める |
| F-9 | 公式手順のmigrationは `npx auth@latest migrate` | #74の「`@latest` を使わない」と合わない | 固定版のライブラリから `getMigrations` をプログラムで呼ぶ方式で再現できた |
| F-10 | DB接続が既定設定のままだと、429の `X-Retry-After` が待ち時間として使えない値になる | node-postgresは `int8` を文字列で返す。Better Auth 1.7.6は `rateLimit.lastRequest`（`int8`）にwindowのミリ秒を足して待ち時間を計算するが、数値へ変換するのは `bigint` 型の値だけで（コードを読んで確認）、文字列のままだと連結になる。観測値は「`lastRequest` とwindowを文字として連結した値」から計算した秒数と一致した（R12）。回数の制限そのものは正しく効く。上流への報告状況は未確認 | 接続poolで `int8` を数値として読むと、再起動後・別のinstance・並列を含むすべての429で1〜60の整数になり、示された秒数の経過後に再び処理された（R1・R2・R5・R6・R7・R11）。安全な整数の範囲を超える値は例外にしている。**この設定は同じpoolを使うアプリ側の `int8` 列にも効く**ため、適用範囲は#74・#75で決める |

**Firebaseとの比較について**：今回Firebaseは実装していない。比較の訂正は [SELECTION-v3.1.md](SELECTION-v3.1.md) に文書として記載した。

**読み取り**

- **同期実行では、計算時間がそのまま他のリクエストの待ち時間になる。** 毎秒1件の予測でも、計算が250msならCRUDのp95は約200ms、500msなら約440msになった。ログインに相当するセッション確認も同じだけ遅れる。
- **計算時間×到着率が1を超えると破綻する。** 500ms×毎秒4件では待ち行列が伸び続け、CRUDのp95が約9秒、DB接続の取得待ちも約3秒になった。DB自体は遅くなく、イベントループが止まって接続を返せないことが原因である。
- **同一プロセス内のworker 2本に移すと、CRUDとセッション確認は計算時間に関係なく数msのままだった。** APIの形もサービスの数も変えていない。
- **T-14の「500ms未満」だけでは足りない。** 単体で500ms未満でも、同期実行なら同時利用者の操作を最大その時間だけ止める。

### 4.2 利用仮定と試算

構成の仮定：Cloud Run 1 vCPU・512MiB・最小instance 0・request課金、Neon 0.25 CU。1か月は30日で計算した。

Cloud RunとNeonでは、数える時間が違う。

- **Cloud Runの課金対象時間**：instanceの起動中、終了処理中、1件以上のリクエストを処理中の時間。instanceが残っていても、処理していない時間は課金されない。同じinstanceで重なったリクエストは、最初の開始から最後の終了までを1回だけ数える。
- **Neonのcompute時間**：computeが起きている時間。最後の問い合わせから5分は起きたままになる。

| 利用の仮定 | Cloud Runの課金対象時間 | Cloud Run | Neon | 合計の目安 |
| --- | --- | --- | --- | --- |
| 開発とデモ。1日30分の利用時間帯を、すべて処理中とみなす | 54,000 vCPU秒、27,000 GiB秒 | 無料枠内 | 0.25 CU × 約15〜20時間。Free枠内 | $0 |
| 日中に継続利用。1日2時間の利用時間帯を、すべて処理中とみなす | 216,000 vCPU秒、108,000 GiB秒 | CPUの超過36,000 × $0.000024 ＝ **$0.86**。メモリは無料枠内 | Free枠内 | 約 $1 |
| 定期アクセスだけが24時間続く。1分間隔、1回の処理は100ms以内、instanceは残っている | 43,200回 × 0.1秒 ＝ 4,320 vCPU秒、2,160 GiB秒 | 無料枠内（CPU枠の2.4%）。リクエスト数も無料枠内 | アクセス先がDBへ問い合わせるなら休止しない。0.25 CU × 720時間 ＝ 180 CU時間。**Freeの100を超えて月の途中で停止**。Launchなら約 $19 | Freeなら $0だがDBが月の途中で止まる。Launchなら約 $19 |
| 24時間、常に1件以上のリクエストを処理中（1 instanceの上限） | 2,592,000 vCPU秒、1,296,000 GiB秒 | CPUの超過分 **約 $58** ＋メモリの超過分 **約 $2** | 同上。Launchなら約 $19 | 約 $80 |

- 上の2行は、利用時間帯のすべてを処理中とみなした上限である。実際の課金対象は処理中の時間だけなので、これより小さくなる。
- 定期アクセスの行は、起動を伴わない場合の計算である。instanceが回収された後のアクセスでは起動時間も課金対象になるが、Cloud Runでの起動時間は未実測で、この分は算定していない。仮にすべてのアクセスが起動を伴っても、起動と処理の合計が1回あたり約4秒までなら月180,000 vCPU秒に収まる（他の利用がない場合）。
- 最後の行のリクエスト数の料金は、件数の前提を置いておらず未算定（月200万件まで無料）。

その他：Secretは3個程度なら無料枠内。イメージを5世代残すと約1.25GiBで月 $0.08程度。通信とログは、転送量とログ量の前提を置いておらず未算定（単価と無料枠は§4.1）。LLMは提供元が未定のため試算していない。

### 4.3 有料化が必要になる条件

- **復旧可能期間**：NeonのFreeは6時間まで。翌日に気付いた誤削除は戻せない。デモ前に手動snapshotかdumpを取る。長い履歴が要るならLaunch。
- **DB容量**：0.5GBを超えると書き込みが失敗する。今回のデータモデルでは当面届かない見込みだが未計測。
- **常時応答**：休止後の遅延が許容できなければ最小instance 1（月 約 $10の試算）とNeonの常時稼働が要る。
- **定期アクセスに注意**：5分以内の間隔でDBへ届く監視やポーリングは、Neonのcomputeを休止させず、月180 CU時間になってFreeの100 CU時間を超える。Cloud Runは処理中の時間だけが課金対象なので、定期アクセスだけでは無料枠を使い切らない（1分間隔・1回100msで月4,320 vCPU秒）。Cloud Runが無料枠を超えるのは、処理時間の合計が月180,000 vCPU秒（1 vCPUで50時間）を超えたときである。

### 4.4 今は不要な構成要素

最小instance 1、Redis、Cloud SQL、ロードバランサとCDN、独自ドメイン、メール配信、OpenAPI生成とclient生成、別サービスとしてのworker、メッセージキュー。
