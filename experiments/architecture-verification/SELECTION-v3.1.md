## 2. 認証：訂正後の比較

Firebaseは今回実装していない。以下は公式資料に基づく机上の比較で、Better Auth側だけが実測である。

| 観点 | Better Auth | Firebase Authentication |
| --- | --- | --- |
| メール／パスワード、未認証の遮断 | 実測で確認 | 可能 |
| 同一originのHttpOnly Cookie | 組み込み。実測で確認 | 可能。IDトークンをセッションCookieへ交換する経路、CSRF対策、失効の確認方針を自分たちで設計する |
| 認証データの置き場 | アプリと同じPostgreSQL | Google側。米国で処理 |
| アプリデータとの整合 | 同じDBで外部キーを張れる。原子的な削除を設計できる | DBをまたぐ。削除は冪等な再試行が要る |
| レート制限 | DB保存で、再起動・複数instance・並列でも上限を守ることを実測 | Google側の保護に任せる |
| Cloud Runでの資格情報 | DB接続文字列と署名用Secret | ADCを使える。鍵ファイルは必須ではない |
| 自分たちが担う運用 | ライブラリ更新、認証テーブルのmigration、復旧メール配信、障害対応 | プロジェクト設定、クライアントSDK、Admin SDK、失効方針 |
| 固定費 | なし | 基本認証は無料枠内 |

**Better Authを第一候補にする理由**：管理対象を既存のDBへ寄せられる。認証とアプリデータの整合を設計しやすい。Cookieセッションとレート制限が組み込みで、今回の実測で動作を確認できた。

**逆転条件**：復旧メールの配信、認証ライブラリの更新、障害対応をチームが継続して担えず、マネージドなIdPに任せる利益のほうが大きい場合。

**採用する場合の条件**（検証で確認した対処）：

- レート制限はDB保存にする。
- 変換routeは公式ガイドのままにせず、信頼するproxyのhop数からクライアントIPを1つに決めて渡す。ガイドのままだと、転送ヘッダーが複数値のとき全クライアントが1つのバケツを共有する。
- 認証エンドポイント全体の上限（既定は1IPあたり60秒100回）を、共有回線を想定して設計する。
- migrationは固定版のライブラリからプログラムで実行する。
- 本番のbase URLはhttpsにする。Cookieに `Secure` が付く。

**長期運用の未決事項**：パスワード再設定をデモ範囲から外す判断はあり得るが、実ユーザーに公開する前に、復旧手段、担当、導入時期を決める。

## 3. 契約とフレームワーク

### 共有スキーマで始め、OpenAPI生成はfreeze後

変更なし。検証では、同じTypeBoxスキーマをFastifyの入力検証・応答serializationと、Webの型・`/today` 応答の実行時検証に使えることを確認した。Web bundleにサーバー専用コードは混ざらなかった。

型のimportだけでは、route、method、status、error形式のずれを防げない。次の対応表を契約試験で確認する。

| Issue | method / path |
| --- | --- |
| #76 | `GET /api/goals`、`POST /api/goals`、`GET /api/goals/:goalId`、`PATCH /api/goals/:goalId`、`DELETE /api/goals/:goalId` |
| #77 | `PUT /api/goals/:goalId/logs/:localDate`、`GET /api/goals/:goalId/logs`、`GET /api/goals/:goalId/today` |

### FastifyとHono

比較の結論はv3と同じで僅差。今回はFastifyだけを動かしたので、差は縮まっても広がってもいない。Fastifyを選ぶ場合に自分たちが引き受ける作業が、実測で具体的になった。

| Fastifyで必要だった作業 | 内容 |
| --- | --- |
| 入力検証を厳格にする | 既定設定は未定義の項目を捨て、型を変換してから検証する。status別の契約では違反が通ってしまう |
| 422と項目別のerror形式 | 既定は400で、最初の1件だけ |
| Type Providerの再適用 | pluginスコープごと |
| Better Authの変換route | 約30行。クライアントIPの渡し方を直す必要がある |

Honoなら変換routeは1行で済むが、応答の検証、構造化ログ、終了処理を自分たちで組む点は変わらない。**API担当の習熟度で決める**という判断は維持する。

TanStack Startを第一候補にしない理由も変更なし。HTTPのAPI契約が確定しており、server functionsの利点が小さくなる。公式表記はRC。

## 4. `/today` の読み取り順

1. セッションを検証する。
2. 所有者条件を付け、Goalと対象logsを1つのsnapshotで取得する。
3. 1回だけ読んだ時計と、そのsnapshotのGoalのtimezoneから `today`・`yesterday` を導出する。
4. DB接続を返してから予測を計算する。
5. 既存契約のDTOに写して返す。

検証では、Goalとlogsを1つのSQL文で取得する形で実装し、動作を確認した。1文で済まない場合は、同じ短いtransaction内で完結させ、分離レベルを選ぶ。公開APIの形は変えない。

## 5. 性能の判断方法

- **単体計算**：#73のT-14。予測エンジンが未実装のため未実施。
- **配置と同時実行**：混合負荷。代用の計算で実測した結果、同期実行では計算時間がそのままCRUDとセッション確認の待ち時間になり、同一プロセス内のworker 2本に移すと数msのままだった。
- **方針**：エンジン実装後にT-14を測る。計算が100msを超えるなら、同一プロセス内のworker poolで実行する。別言語や別サービスへの変更は検討しない。

## 7. プレゼンで話す選定理由（案）

実装とテストが済むまでは、次の形にする。

> 予測は本人の記録から閉形式と動的計画法で計算する純関数にして、UI・DB・HTTP・時計から切り離し、性質ベースのテストで不変条件を検証する設計です。サーバーは「今日」の決定、所有者の確認、記録ルール、正本の予測を担います。入力と応答の形をスキーマとして1か所に定義し、APIと画面が同じ契約を参照します。3人で作るので言語は1つ、配備は1つのコンテナと1つのDBに絞り、責務はモジュールで分けます。

テストの実行後に、環境・範囲・結果を添えて過去形にする。性質ベーステストの成功は、あらゆる入力に対する数学的保証ではない。
