## 2. 認証：訂正後の比較

Firebaseは今回実装していない。以下は公式資料に基づく机上の比較で、Better Auth側だけが実測である。

| 観点 | Better Auth | Firebase Authentication |
| --- | --- | --- |
| メール／パスワード、未認証の遮断 | 実測で確認 | 可能 |
| 同一originのHttpOnly Cookie | 組み込み。実測で確認 | 可能。IDトークンをセッションCookieへ交換する経路、CSRF対策、失効の確認方針を自分たちで設計する |
| 認証データの置き場 | アプリと同じPostgreSQL | Google側。米国で処理 |
| アプリデータとの整合 | 同じDBで外部キーを張れる。原子的な削除を設計できる | DBをまたぐ。削除は冪等な再試行が要る |
| レート制限 | DB保存で、再起動・複数instance・並列でも上限を守ることを実測 | Google側の保護に任せる |
| Cloud Runでの資格情報 | DB接続文字列と署名用Secret | ADCを使える。鍵ファイルは必須ではない |
| 自分たちが担う運用 | ライブラリ更新、認証テーブルのmigration、復旧メール配信、障害対応 | プロジェクト設定、クライアントSDK、Admin SDK、失効方針 |
| 固定費 | なし | 基本認証は無料枠内 |

**Better Authを第一候補にする理由**：管理対象を既存のDBへ寄せられる。認証とアプリデータの整合を設計しやすい。Cookieセッションとレート制限が組み込みで、今回の実測で動作を確認できた。

**逆転条件**：復旧メールの配信、認証ライブラリの更新、障害対応をチームが継続して担えず、マネージドなIdPに任せる利益のほうが大きい場合。

**採用する場合の条件**（検証で確認した対処）：

- レート制限はDB保存にする。DB接続は `int8` を数値として読む設定にする。既定のままだと、429の待ち時間ヘッダーが異常値になる（[REPORT.md](REPORT.md) のF-10）。
- 変換routeは公式ガイドのままにせず、信頼するproxyのhop数からクライアントIPを1つに決めて渡す。ガイドのままだと、転送ヘッダーが複数値のとき全クライアントが1つのバケツを共有する。
- 認証エンドポイント全体の上限（既定は1IPあたり60秒100回）を、共有回線を想定して設計する。
- migrationは固定版のライブラリからプログラムで実行する。
- 本番のbase URLはhttpsにする。Cookieに `Secure` が付く。

**長期運用の未決事項**：パスワード再設定をデモ範囲から外す判断はあり得るが、実ユーザーに公開する前に、復旧手段、担当、導入時期を決める。

### 共有スキーマで始め、OpenAPI生成はfreeze後

### FastifyとHono

比較の結論はv3と同じで僅差。今回はFastifyだけを動かしたので、差は縮まっても広がってもいない。Fastifyを選ぶ場合に自分たちが引き受ける作業が、実測で具体的になった。

| Fastifyで必要だった作業 | 内容 |
| --- | --- |
| 入力検証を厳格にする | 既定設定は未定義の項目を捨て、型を変換してから検証する。status別の契約では違反が通ってしまう |
| 422と項目別のerror形式 | 既定は400で、最初の1件だけ |
| Type Providerの再適用 | pluginスコープごと |
| Better Authの変換route | 約30行。クライアントIPの渡し方を直す必要がある |

Honoなら変換routeは1行で済むが、応答の検証、構造化ログ、終了処理を自分たちで組む点は変わらない。**API担当の習熟度で決める**という判断は維持する。

TanStack Startを第一候補にしない理由も変更なし。HTTPのAPI契約が確定しており、server functionsの利点が小さくなる。公式表記はRC。

## 4. `/today` の読み取り順

1. セッションを検証する。
2. 所有者条件を付け、Goalと対象logsを1つのsnapshotで取得する。
3. 1回だけ読んだ時計と、そのsnapshotのGoalのtimezoneから `today`・`yesterday` を導出する。
4. DB接続を返してから予測を計算する。
5. 既存契約のDTOに写して返す。

検証では、Goalとlogsを1つのSQL文で取得する形で実装し、動作を確認した。1文で済まない場合は、同じ短いtransaction内で完結させ、分離レベルを選ぶ。公開APIの形は変えない。

## 5. 性能の判断方法

- **単体計算**：#73のT-14。予測エンジンが未実装のため未実施。
- **配置と同時実行**：混合負荷。代用の計算で実測した結果、同期実行では計算時間がそのままCRUDとセッション確認の待ち時間になり、同一プロセス内のworker 2本に移すと数msのままだった。
- **方針**：エンジン実装後にT-14を測る。計算が100msを超えるなら、同一プロセス内のworker poolで実行する。別言語や別サービスへの変更は検討しない。

## 7. プレゼンで話す選定理由（案）

実装とテストが済むまでは、次の形にする。

> 予測は本人の記録から閉形式と動的計画法で計算する純関数にして、UI・DB・HTTP・時計から切り離し、性質ベースのテストで不変条件を検証する設計です。サーバーは「今日」の決定、所有者の確認、記録ルール、正本の予測を担います。入力と応答の形をスキーマとして1か所に定義し、APIと画面が同じ契約を参照します。3人で作るので言語は1つ、配備は1つのコンテナと1つのDBに絞り、責務はモジュールで分けます。

テストの実行後に、環境・範囲・結果を添えて過去形にする。性質ベーステストの成功は、あらゆる入力に対する数学的保証ではない。

| --- | --- |
| 何に使うか | PostgreSQLへGoalと日ごとの記録を保存する。Better Authを選ぶ場合は認証データも保存する。`pg`はDB接続、SQLは取得・制約・更新、migrationはDB構造の変更履歴を再現する役割 |
| このProductに合う理由 | 「1 Goal・1日1件」、Goalと記録の参照関係、本人だけの読み書きが中心。DBの一意制約・外部キー・transaction（複数の変更を一まとまりにする処理）で整合を支えられる。主要アプリテーブルは2つなので、SQLを直接読む案は記録や所有者条件の確認箇所を追いやすい。認証テーブルが別にあることを含めて保守する |
| 比較した候補と選ばない理由 | SQLiteも一意制約・transactionを扱えるが、この公開候補では永続ファイル・バックアップ・複数instanceの扱いを自分たちで設計する負担が残る。Drizzle/PrismaはDB自体の代替ではなくSQLを書く層の代替。現行規模で別のスキーマ定義やツール更新を加える利益がまだ示されていない |
| 弱点・残条件 | SQL側とDTO（APIへ返すデータ）の対応、接続pool、migrationと復旧を自分たちで確認する必要がある。`int8`の数値変換（F-10）は同じpoolのアプリ列にも影響するため適用範囲を決める。`node-pg-migrate`は候補で、#85はそのツール選定を実測した証拠ではない |
| 資料・検証範囲 | [REPORT §3.1](REPORT.md#31-検証1認証とdb)で空DBからの再現、重複・状態と量の制約、SQLでの連鎖削除とrollbackを確認。[正式Data Model](../../docs/architecture.md#data-model)と検証コードには差分がある。SQLite・ORM比較、Better Authの削除経路、クラウドの復元は未確認 |

### 認証：Better AuthとManaged認証

| 観点 | 説明 |
| --- | --- |
| 何に使うか | メールとパスワードの登録・ログイン・ログアウト、DBに保存するセッション、認証操作のレート制限。Goalの所有者確認はAPI側の責務として残る |
| このProductに合う理由 | 認証とGoal・記録を同じPostgreSQLへ寄せると、データの参照関係と削除・復旧を一緒に設計しやすい。外部の認証サービスを増やさない案で、#85では接続と失効、DB保存の制限を確認できた。ただしライブラリを使うことは運用責任を外部へ任せることではない |
| 比較した候補と選ばない理由 | Firebase Authentication・Supabase Authは運用をManagedサービスへ寄せる代替候補。今回は認証データとアプリDBの境界を増やすより、同じDBに寄せる案を先に検証した。自作認証はパスワード・セッション・復旧の安全性を継続して保守する責任が大きい。Managed案との総費用・障害復旧の比較は不足しており、不採用の確定根拠にはしない |
| 弱点・残条件 | ライブラリ更新、認証migration、復旧メール・障害対応を担当できること。F-5のproxy/IP、F-10の待ち時間、DB保存のレート制限を対処し、共有回線の上限を決める。アプリrouteのCSRF方針と実ブラウザ確認は未完了。パスワード再設定を入れないデモの公開範囲、継続一般公開の前に入れる時期・担当を決める必要がある |
| 資料・検証範囲 | [REPORT §3.1](REPORT.md#31-検証1認証とdb)と[§2の比較訂正](#2-認証訂正後の比較)。Better Authのみローカル実測で、セキュリティ監査ではない。[FirebaseのセッションCookie](https://firebase.google.com/docs/auth/admin/manage-cookies)・[Admin SDKのADC](https://firebase.google.com/docs/admin/setup)・[Better Authのセッション管理](https://www.better-auth.com/docs/concepts/session-management)は2026-10-02に公式資料を確認 |

FirebaseもセッションCookieを使え、Cloud RunでADC（実行環境の認証情報を使う方式）を利用できる。Cookieや鍵ファイルの有無を不採用理由にしない。Better AuthからManaged認証へ推奨を変える条件は、機能の有無ではなく**更新・復旧・障害対応をチームが継続して担えるか**。§2の「固定費なし」はライブラリ利用料の比較で、DB・メール・担当者の保守負担を含む総費用がゼロという意味ではない。

### 構成と予測：1アプリと独立した計算コア

| 観点 | 説明 |
| --- | --- |
| 何に使うか | モジュラーモノリスは配備するアプリを1つにし、内部のauth・Goal・記録・予測adapterのコードを分ける案。計算コアはHTTPやDBを持たず、入力から予測結果を返す純粋関数にする |
| このProductに合う理由 | 予測は本人の記録とGoalの日付に依存する。境界を明確にすると、Webの表示変更やDB・認証の更新を計算へ持ち込まずに済む。1つのアプリならサービス間通信と配備・監視の対象を抑えられる。計算コアが独立しているので、テストと性能改善は別に行える |
| 比較した候補と選ばない理由 | 別言語の予測サービス、Microservices、Queue、Redisは、現行要件にない通信・非同期の状態・障害復旧を増やす。将来の増加だけを理由に初期導入しない。LLMやML frameworkは、採用済みの閉形式・DPの計算に必要ない。予測モデルM0/M2や将来の日々のMonte Carloの不採用理由は[既存の判断記録](../../docs/prediction/decision-log.md)にあり、ここで再選定しない |
| 弱点・残条件 | 1アプリでも同期CPU計算はAPIを止めうる。まず本実装でT-14の500ms未満を維持して計測し、実エンジンとCRUD・認証の混合負荷を確認する。worker pool（計算用のスレッドを再利用する仕組み）の採否・キュー上限・1 vCPUでの効果は未決定。利用増加で待ち時間や費用の許容範囲を超えたらworker、CPU・DB接続数の調整を検討し、それでも足りない証拠が出てからサービス分離を再検討する |
| 資料・検証範囲 | #85の[混合負荷](REPORT.md#32-検証2予測性能)は代用CPU計算で、実エンジンの測定ではない。その後の[予測Evidence](../../docs/prediction/evidence.md#dpとmonte-carloの比較)には刈り込みありの試作DPで最大約260msの記録がある。本実装のT-14、実エンジン混合負荷、Cloud Run性能、同時利用可能人数を証明しない |

予測方式とのつながりは[Architecture D-19〜D-22](../../docs/architecture.md#d-19)を入口に読む。中心指標は再開までの日数を閉形式で計算し、分位点の境界を整数で厳密に比較する。完了の目安は事後サンプルごとのDPで求める。誇張や計算ノイズを抑える決定が、独立した計算コアと決定的なテストを必要にしている。

| 分担 | 今回の提案による境界 | 正本・確認先 |
| --- | --- | --- |
| FE | APIが返す状態・`null`・日付を表示し、記録保存後に再取得する。予測を別計算しない。基盤合意後のモック作業と本接続を分けるが、着手範囲は対象Issueの承認記録に従う | [表示仕様](../../docs/product-spec.md#today-decision画面の表示仕様)、[Issue運用](../../docs/DEVELOPMENT_GUIDE.md#着手前に読み直す)、[PR #92の確認](https://github.com/jogi-hack-2026-team/jogi-hack-2026/pull/92#issuecomment-5944800922) |
| BE | 認証、所有者、記録可能日、入力検証、保存とEngineへの入力を担当。`/today`のsnapshot・時計1回・接続を返してから計算する順は提案のままで、合意後に反映する | [API契約](../../docs/architecture.md#api契約)、[契約差分の未合意表](../../docs/architecture.md#検証コードとの差分変更案未合意) |
| Engine | 渡されたGoal・記録・`today`だけで計算し、時計・DB・HTTPに依存しない。既存モデルとテストの不変条件を守る | [Prediction Engine](../../docs/architecture.md#prediction-engine)、[T-01〜T-15](../../docs/architecture.md#test-strategy) |

### 配備：Cloud RunとNeon

| 観点 | 説明 |
| --- | --- |
| 何に使うか | Cloud Runは1コンテナでWeb/APIを公開する候補、NeonはPostgreSQLの管理を任せる候補。同一originで配信する形ならWebとAPIの公開先を分けずに済む |
| このProductに合う理由 | 利用が少ない時間の計算資源を抑え、常時起動の固定費とDBサーバー自体の保守を減らす狙い。サービスを止められる時間があるデモ・初期利用に合う可能性がある。低費用を狙えることと、休止後にも快適に使えることは別に確認する |
| 比較した候補と選ばない理由 | Cloud SQLは#85の比較では当初構成に含めない候補で、継続運用・同地域の利益と月額の比較が不足。VPSでアプリとDBを持つ案は、サーバー・DBの更新、バックアップ、障害復旧を自分たちで持つことになる。旧音楽案のProvider比較は当時の要件・料金の履歴であり、現行の優劣の証拠にしない。どれが最安かは未確定 |
| 弱点・残条件 | リージョン間の遅延、両方の休止後の応答、コンテナ、HTTPS/Cookie、proxyの実形式、DB接続数、1 vCPUでの混合負荷が未確認。#85ではNeonに東京がないことを記録しているため作成前に提供地域と組み合わせを再確認する。容量・復旧可能期間・復元担当・月額予算を決める。アカウント・課金・staging作成は別の承認が必要 |
| 資料・検証範囲 | [REPORT §3.3](REPORT.md#33-検証3配備と費用)はローカルのSPA/API経路と終了処理のみ。[費用 §4](REPORT.md#4-費用の前提)は公式料金を2026-09-30確認、課金対象時間を2026-10-01訂正した机上試算。配備先の性能・費用は未実測。今回[Cloud Run公式料金](https://cloud.google.com/run/pricing)は確認できたが、[Neon料金](https://neon.com/pricing)・[提供地域](https://neon.com/docs/introduction/regions)は本文を再取得できず、新しい料金・地域の断定は追加していない |

月額の読み方はREPORT §4.2の利用仮定を参照する。記録時点の試算は、30日・Cloud Run 1 vCPU/512MiB/最小instance 0・Neon 0.25 CUで、デモ利用が約$0、1日2時間をすべて処理中とみなす場合が約$1。これは**通信・ログ・LLM・運用作業等を含む総月額ではなく、無料枠内を保証しない**。DBへ1分ごとに問い合わせる監視はNeonを休止させず、無料枠超過の要因になる。Cloud Runはidleを含む常時起動時間ではなく課金対象の処理時間を数えるため、初回コメントの「定期アクセスで約$80」を採用理由に使わない。
