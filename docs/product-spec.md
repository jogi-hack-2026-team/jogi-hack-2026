## Product Overview

| 項目 | 内容 |
| --- | --- |
| Problem | 今日行動しないことによる将来への影響が見えず、「今日はやらなくてもいいか」と判断しやすい |
| Target User | 毎日取り組みたい、量で表せる継続行動を持つ人（英語学習、資格勉強、読書、コーディング学習、毎日の運動など）。MVPは「毎日1回の実行機会がある行動」に限定する |
| Core Value | 自分の記録から、今日やらなかった場合に、自分で決めた努力量への到達がどれくらい後ろへずれるかを見える化する |
| Hero Copy | **今日サボると、ゴールは何日遠ざかる？** |
| 意味の範囲 | 今日実行しなかった場合、次に実行状態へ戻るまでにかかる日数だけ、設定した累積努力量への到達時期が後ろへずれる |
| Need Validation | 未検証。表示が今日の行動判断に役立つかはProduct Hypothesisとして扱う |

### Future ROIがしないこと

- 成果そのもの（TOEICの点数、体重、合格）の達成日を予測しない。予測対象はユーザーが決めた累積努力量への到達だけ。
- 「サボると雪だるま式に未来が悪化する」とは言わない。
- 因果効果を主張しない。記録から推定した傾向が今後も続くと仮定した計算である。
- 習慣の強さを測定すると主張しない。
- LLMに予測・必要努力量の決定をさせない。

## Core User Flow

1. ユーザーがアカウントを作成してログインする。
2. Goalを作成する（タイトル、単位、投資すると決めた総量、1回の量、記録開始日の前日までに終えた量。初期値0）。
3. 毎日、今日のDONE / SKIPPEDを記録する。昨日が記録開始日以降で未記録なら「昨日はどうでしたか？」で補完できる。今日から記録を始めるGoalでは昨日分を追加せず、翌日に今日の記録漏れを補える。
4. 休んだ翌日の記録がたまると、「今日サボると約○日遠ざかる」を確認できる。
5. 今日やるかを判断し、DONE / SKIPPEDを記録する。

開始時の質問・仮の見通し・条件付き計画を加えるFlowは[R-11のレビュー案](#質問から始める見通しr-11)。回答状況と採択する表示条件によって値の可否が異なり、全員に仮の予測を常時表示する仕様ではない。

### Today Decision画面の表示仕様

下表は現行の実績由来モードの表示。R-11の回答由来モードは未採択案であり、「あなたの記録から」や実績件数を流用しない。回答由来の注釈・表示可能条件・不足時の文言は下の未決事項で具体化する。今日記録済み（R-07）・達成済み（R-08）の優先と補助指標2つまでの規則は維持する。

| 要素 | 文言 | 値の出どころ |
| --- | --- | --- |
| 見出し | 今日サボると、ゴールは何日遠ざかる？ | — |
| 中心指標 | ゴールが遠ざかる日数（目安）：**約{g50}日** | [Prediction Engine](architecture.md#prediction-engine)の`coreMetric.g50` |
| 中心指標の注釈 | あなたの記録から推定した「休んだ後の再開傾向」をもとに計算しています。今日やらなかった場合、次に再開するまでの日数だけ完了が後ろにずれる、という見込みで、将来を保証するものではありません。 | — |
| 補助指標1 | 休んだ翌日にやれたのは **{nSD+nSS}回中{nSD}回** | `observations` |
| 補助指標2 | 今日やった場合の完了の目安：**{p50の週}ごろ**（10回中8回は{p80の週}まで） | `completion`。日付はその日を含む週の月曜日で表示する。3年を超える場合は「3年以上先」 |
| 補助指標2の注釈 | 完了の目安は、同じ記録から推定した継続傾向でシミュレーションした見込みです。 | — |
| データ不足（中心指標） | まだ「休んだ翌日」の記録がありません。記録がたまると、あなたの再開傾向から推定します。 | `coreMetric.status = insufficient` |
| データ不足（完了の目安） | 「やった翌日」と「休んだ翌日」の記録がそれぞれたまると、完了の目安を表示します。 | `completion.status = insufficient` |

中心指標を「シミュレーション」と呼ばない（閉形式の計算であるため）。「今日やれば○日早くなる」と断定する表現、損失を強調して休んだ日を責める表現を使わない。

操作ボタンの文言は「やった」「今日は休む」。見出しの「サボる」と操作の「休む」の語の違いは、I-12の簡易ユーザー確認で「今日休むと、ゴールは何日遠ざかる？」と比べる。見出しを変える場合はP-12の改訂として記録する。

### 質問から始める見通し（R-11）

実績のない開始時にも判断材料を作るため、依頼者は回答から初期の確率分布を置き、実際の隣接する記録で更新する機能のMUST追加を求めている。採択の場はPR #115とし、チームの判断は未完了。採択案では、開始時の任意質問から回答状況に応じた仮の見通し等へ進み、実際の記録で更新する。質問の答えが実際の行動確率を正しく測れるか、表示が行動を助けるかは未検証。回答から過去の記録を作らず、R-02・P-14の初期量と日々の記録の境界を守る。

機能追加の判断だけでは以下を採択しない。具体案は[PR #108の公開提案](https://github.com/jogi-hack-2026-team/jogi-hack-2026/blob/a4c383b1b2bc95e4a838727e5b7e4e28bb261ec0/docs/prediction/question-prior-proposal.md)を参照し、人間の判断後に正本・共通契約・既存Issueへ反映する。

#### 初期質問のレビュー用たたき台

2026-10-05、依頼者が以下の質問文を「レビュー対象にして一旦たたきとしてこれで行こう」と承認した。MUST機能の採用方針と、レビュー用文案の選択を分ける。文言・追加分岐・数値写像・強さ・表示・API契約は最終採択ではない。

機能をMUSTとして提供することは、各Goalで回答を必須にする意味ではない。今回のたたき台では、Goal作成・編集のたびに回答を強制せず、入力負担と取り組み開始を妨げないことをレビューする。

説明文：

> 最初の見通しを作るために、これまでの取り組み方を教えてください。今回の目標に近い内容・量を思い浮かべて答えてください。分からなくても大丈夫です。

| 質問 | レビュー用の文言 | 現行モデルとの対応 |
| --- | --- | --- |
| Q1 | 取り組めた日の翌日も、続けて取り組むことはどのくらいありましたか？ | やった翌日にやる傾向（a） |
| Q2 | お休みした日の翌日に、また取り組むことはどのくらいありましたか？ | 休んだ翌日にやる傾向（b） |

共通の選択肢：

- 少なかった（4回に1回くらい）
- 半分くらい（4回に2回くらい）
- 多かった（4回に3回くらい）
- 経験がない・思い出せない

補足文：これからの意欲や理想ではなく、実際の過去の取り組み方を答えてください。経験がない・思い出せないときは、無理に選ばなくて大丈夫です。

選択肢の回数は回答の目安であり、4回の実績・遷移を作らない。回答から初期分布への写像とその重みは別の採択事項で、未回答・不明を本人が「半分」と答えた扱いにしない。回答由来の見通しと実際の記録・件数を分ける。

**2問で十分か：** 現行モデルが使う「やった翌日」「休んだ翌日」の2つの傾向に対応する入口であり、2問だけで行動を十分に説明できる、予測精度が十分である、とは判断していない。対象となる経験・量・生活状況が今回と近いか、回答を思い出せるかが別に必要。外部の設計指針や他分野の事前分布研究を参考にしても、この文言・3段階の数値対応・強さが校正済みになったとは扱わない。

**追加のレビュー候補（分岐は未承認）：** 先に「今回の目標に近いことを、これまでも続けていましたか？」と経験を確認する。経験ありなら2問へ進み、初めて・量や生活が大幅に変わった場合はa／bを無理に答えさせず、条件付き計画へ進む案。条件付き計画は「毎日1回、設定量を行うなら残り何回か」という前提付きの計画で、個人の行動確率や予測ではない。導入する場合も補助指標2つまでのP-12と表示位置を照合する。この追加質問・分岐・表示を本項で確定しない。

**入力負担のレビュー候補（未採択）：** Goal作成時の任意セクションを「最初の見通しを調整する」とし、スキップして作成できる案。未回答は条件付き計画へ進め、Goal編集や別Goal作成のたびに回答を強制しない。別Goalへ回答を黙って流用せず、同じ行動・量・文脈として再利用できる範囲や確認方法はD-26で判断する。セクション名・スキップ時の表示・再利用方法の最終採択ではない。

**未回答時の回数表示候補（レビュー対象）：** 未達成なら、残量は`totalRequired − actualDone`、必要回数は残量を`sessionAmount`で割って切り上げる。例として100問の目標・60問済み・1回15問なら、残り40問なので「あと3回分」、最後に必要な量は10問。これは設定量を行う場合の条件付き回数であり、3日で終えるという予測ではない。1日1件の記録とDONEの実量入力という既存契約に沿って扱い、1日に複数セッションを登録する仕様や新しいGoal型・単位は追加しない。達成済みではR-08を優先する。短期Goalでのスキップと回数表示の方向は依頼者が了承したが、具体の分岐・表示文言・受け渡すAPI項目は引き続きレビュー対象とする。

| レビュー論点 | 確認すること |
| --- | --- |
| 「取り組む」とDONE量 | 少量でもDONEとして実量を記録できる現行契約と、質問を「1回量を終えた頻度」と読む場合のずれを確認する。質問案からDONEの閾値を変更しない |
| 参照期間・文脈 | どの期間の経験を答えるか、今回と近い行動・量・生活状況か。長期間や異なる経験を同じ確率としてまとめてよいかは未確認 |
| 片方回答・不明 | Q2だけで中心の仮の値を出すか、完了にはQ1・Q2両方の材料を求めるか、Q1だけ／両方不明なら何を表示するかを採択する。共通初期値を本人の回答として表示しない |
| Goalごとの入力負担 | 質問を省略してもGoalを作れるか、編集や別Goalで答え直しを強いていないか。異なる行動・量の回答を本人の現在の傾向として黙って使わない |
| 1〜2日で終えたい短期Goal | 短期でも質問を任意でスキップできるか、条件付き計画の「あと何回分」と完了日予測を混同させないか。2日以下の自動除外や単発／継続の新Goal型は採用していない |
| 回答と記録の理解 | 「翌日」を数日後の再開と混同しないか、未来の意欲を答えていないか、回答が実績として表示されていないかを確認する。表示理解・精度・行動促進効果は未検証 |

### P-14 記録のルール

2026-09-30 / **DECIDED（依頼者判断）** / 記録はDONE / SKIPPEDの2値。記録のない日はUNKNOWNとして扱い、SKIPPEDとみなさない。記録できるのは今日と昨日だけ（昨日は補完用）。記録が1件でもあるGoalはtimezoneと記録開始前の量を変更できない（過去の日付の基準と予測の意味を変えないため）。やらなかった日ほど記録されない偏りは統計的に補正せず、前日補完のUXで減らす。偏りはKnown Limitationとして[Architecture](architecture.md#known-limitations)に記録する。

2026-10-03 / **依頼者指示による明確化（文書反映、実装未検証）** / 今日・昨日の範囲を維持し、昨日の誤記も訂正できるものとして上記の「補完用」を明確化する。以下は記録の意味と理由であり、新しい画面の実装完了を示さない。

- UNKNOWNは「分からない」であり、休んだ証拠ではない。未記録を自動でSKIPPEDにせず、「後で答える」でも行を作らない。記録済みをUNKNOWNへ戻す削除・取消操作は未採択。
- 記録は「いつ入力したか」ではなく「いつ行動したか」に付く。今日入力する昨日分は昨日の記録として明示し、同じGoal・行動日への保存は既存の記録を置き換える。入力のたびに実績を加算すると、訂正・再送で量が増えてしまうため、現在の記録から再計算する。
- 記録開始日以降の昨日のDONEは実際の量を確認・訂正できる。`sessionAmount`は入力の既定値と将来計算用の量であり、変更しても保存済みのDONE量を書き換えない。初期進捗との境界は下の承認済み追補に従う。
- 今日・昨日だけに限る理由は、MVPのMust完成に向けて入力・訂正・日付境界の実装と確認を抑え、直近の記録忘れと誤記に対応するため。科学的に最適な日数という根拠はない。7日間など長い範囲の編集は、記憶違い・訂正負担・再計算への影響を比較する将来候補であり、今回は採用しない。
- 前日補完は記録忘れを減らす狙いで、効果は未検証。UNKNOWNを含むペアを除いても、休んだ日ほど未記録になる偏りは解消しない。予測は記録されたデータに基づく見立てである（[限界と研究の位置づけ](architecture.md#known-limitations)）。

現在の分担は[#77](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/77)が今日・昨日のPUT上書き、[#79](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/79)が今日の変更と再取得、[#80](https://github.com/jogi-hack-2026-team/jogi-hack-2026/issues/80)が昨日未記録時の問いかけ。記録済みの昨日を訂正する入口・担当は不足しているため、3 Issue間で調整する。未記録時だけの問いかけを訂正UIとして兼用しない。画面・APIの実装と統合は別途必要で、既存のHard依存を解除しない。[受入確認](architecture.md#記録補完訂正の受入確認)へ追跡する。

2026-10-03 / **DECIDED（依頼者承認「いいと思う」、境界方針のみ）** / 初期進捗は記録開始日の前日まで、日々の記録は記録開始日以降に分ける。許可窓は「Goalのtimezoneで今日・昨日」かつ「記録開始日以降」。登録時の累計に含まれる昨日の量を再び加算しないためであり、初期量を減算して開始日前のログを追加する前案は採用しない。初期進捗から過去のDONE / SKIPPEDや遷移を作らない。開始日は初回ログの保存を遅らせても動かさない。[作成日の暦日を使う最小案・保存方式・既存Goalの互換性](architecture.md#初期進捗と日々の記録の境界)は別途具体化する。日数metadataの数え方はこの承認に含まれない。

画面文言：初期量の欄は「記録開始日の前日までに終えた量」、初期値は0。説明は「記録開始日：{開始日}。この日以降の実績は日々の記録に入力してください。開始日前の分はこの累計に含め、日々の記録には追加しません」。今日から開始する場合は昨日の問いかけ・訂正を出さず、「昨日までの分は登録時の累計に含めます。今日の記録漏れは明日補完できます」と説明する。文言の反映は未実装で、開始日をFEへ伝える契約は未決。

## Reconsideration Policy

別案の存在だけで現在の判断を覆さない。欠陥、要件未達、規約・安全・運用上の重大リスク、期間超過、同等価値の単純化、一次情報による前提変更、PoCの不成立など、具体的な根拠がある場合に提案する。提案には対象Decision、変更案、根拠、利点・欠点、新しいリスクと移行コストを記録し、**提案→人間Decision→正式反映**の順を守る。旧案の詳細な検討経緯は[履歴](../archive/music-exploration/docs/product-spec.md#reconsideration-policy)に残す。
