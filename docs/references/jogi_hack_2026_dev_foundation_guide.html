開発基盤・開発ルールガイド

3人・約3週間のWebアプリ開発で、環境差・仕様の認識ズレ・レビュー待ち・Secret共有事故・コードフリーズ直前の混乱を減らすための意思決定と運用ルールをまとめる。技術を増やすことではなく、「なぜ必要か」をチーム自身が説明できる状態を目的とする。

開発期間 2026-09-19 → 2026-10-12 Team 3 Web Application Code Freeze 2026-10-12 API / DB 利用可能性：高

この資料の立場

現時点で確定

  • 3人チーム
  • Webアプリケーション
  • 開発期間とCode Freeze
  • ソースコード・アーキテクチャも審査対象
  • API / DBを使う可能性は非常に高い

現時点で未確定

  • AI、認証、Hosting、外部API
  • Redis / Queue / Worker / SSE / WebSocket
  • DDD / Clean Architecture等の設計手法

2. Design Principles

技術スタックを先に固定しない。プロダクト固有の問題を起点に、必要な性質へ落とし込み、その後で実装技術を選ぶ。

Problem First

課題 → 必要機能 → 必要な技術的性質 → 技術選定、の順を崩さない。

Necessary Complexity

必要な複雑性だけを持つ。MicroservicesやQueue等を「技術的に強そう」という理由では入れない。

Single Source of Truth

同じ情報を複数箇所で管理しない。コード・仕様・進捗・Secretの正本を決める。

3-week ROI

導入・学習・デバッグコストを含め、3週間で元が取れる仕組みだけ導入する。

Explainable Decision

「なぜ？」に対して、比較候補・トレードオフ・採用理由を説明できる状態を維持する。

Finish First

複数の難しい技術を浅く入れるより、Mustを最後まで完成させる。

5.1–5.8 GitHub / Issues / Projects / Flow / PR / Actions

ADOPTEDTiming: Day 1Confidence: High
Overview
Repository・Issue・Project・Pull Request・CIを同じ場所に寄せ、開発の主線をGitHub内で完結させる。
Problem
タスク、コード、レビュー、進捗が別サービスに分散すると、3週間では「どこを見れば正しいか」の確認コストが大きい。
Without It
チャット上の依頼、手作業の進捗更新、Jira↔GitHubの往復、レビュー漏れが起きやすい。
Requirements
IssueとPRのリンク、Board管理、Milestone、CI結果、レビュー履歴、短命Branch、main保護。
Alternatives
Jira、Notion、Confluence、GitFlow。
Decision / Why
GitHub Issues + Projects + GitHub Flow + PR + Actionsを採択。コードとの距離が最も短く、3人・3週間では管理箇所を増やさないメリットが大きい。

Benefits

  • Issue→Branch→PR→Mergeの追跡が容易
  • PR単位で議論とCI結果が残る
  • MilestoneでMVP / Freezeを可視化
  • Issue FormsでFeature/Bug/Spikeを定型化

Drawbacks / Trade-offs

  • 高度なJiraワークフローほど細かい管理はしない
  • GitHub Projectsの設定を増やしすぎると逆に重くなる
  • private repositoryの一部保護機能はプラン条件に依存

Setup

  1. Project BoardをBacklog / Ready / In Progress / Review / Verify / Doneで作成
  2. Priority、Type、Size等の必要最小限のFieldを追加
  3. Issue FormsをFeature / Bug / Spikeの3種類作成
  4. PR Templateを追加
  5. main direct push禁止、PR経由をチームルール化
  6. ActionsでCIを追加

Usage / Team Rules

  • 1 Issue = 半日〜1日程度を目安に小さくする
  • Branch例：feat/42-user-search
  • PRは1つの意味のある変更に絞る
  • 1人以上のReview、CI成功、Verify後にSquash Merge
  • Closes #42等でIssueとPRを関連付ける
Integration: GitHubを中心に、mise / Docker / Dopplerでローカル開発、Actionsで検証、/docsで確定仕様を同じRepositoryに置く。
Review Trigger: 3人で回らないほどIssue/Project管理が重くなった場合のみ簡略化する。

5.9 Docker Compose

ADOPTEDTiming: DB / 依存サービス決定時Confidence: High
Overview
複数の依存サービスをYAMLで定義し、同じ構成をチームで再現する。今回の主対象はDBやRedis等であり、アプリ本体まで必ずContainer化するとは限らない。
Problem
DB Version、Port、初期設定、依存サービスの導入方法がメンバーごとにずれる。
Without It
「AのPCでは動く」が増え、DBの再作成やセットアップ手順が属人化する。
Alternatives
各自ローカルインストール、Dev Container、外部Managed DBのみ。
Decision / Why
API / DB利用可能性が高いため採択。Docker公式でもComposeはservices / networks / volumesを単一YAMLで管理し、開発・テスト・CI等で利用できる。

Benefits

  • docker compose up -dで依存サービス起動
  • DBを簡単に破棄・再作成できる
  • チーム全員で同一Versionを共有

Drawbacks

  • Docker自体の学習・トラブルシュートが必要
  • Docker Desktopのリソース消費
  • 単純構成では過剰になる可能性

Setup

# 例: 実際のDBはプロダクト決定後
services:
  db:
    image: <database-image>
    # ports / volumes / healthcheck を必要に応じて定義

Team Rules

  • 依存サービスのVersionはcompose.yamlで固定する
  • アプリ本体をContainer化するかは必要性で判断
  • DB reset / seedを共通Taskから実行できるようにする
Review Trigger: Dockerが原因の開発停止時間が環境統一メリットを上回る場合。

5.10 mise

ADOPTEDTiming: Day 1Confidence: High
Overview
Runtime / CLIのVersionと、チーム共通Taskをmise.tomlへ記述して共有する。
Problem
Node等のVersion差、READMEに散らばるコマンド、OSごとのセットアップ差。
Alternatives
nvm / Volta / asdf / Nix / Dev Container / package scriptsのみ。
Decision / Why
ツールVersion管理とTask Runnerを1つで担えるため採択。公式ではmise install、mise run、mise.tomlの共有を前提にしている。

Benefits

  • Runtime差を減らす
  • build / test / db-up等のコマンドを統一
  • CIでも同じ設定を再利用しやすい

Drawbacks

  • メンバー全員がmise CLIを入れる必要
  • package scriptsとの責務を重複させない設計が必要

Setup

# 例
[tools]
node = "<version>"

[tasks.dev]
run = "<package-manager> run dev"

[tasks.test]
run = "<package-manager> test"

Team Rules

  • Version要求はmise.tomlへ
  • 複雑なTaskはpackage scriptsや専用Scriptに寄せ、miseは入口を揃える
  • READMEでは「何を打つか」よりmise runの入口を案内
Review Trigger: 技術スタックがmise非対応またはCI/メンバー環境で不安定な場合。

5.11 Doppler

ADOPTEDTiming: Day 1Confidence: High
Overview
API KeyやDATABASE_URL等のSecretを集中管理し、ローカルやCIへ注入する。SecretのSingle Source of Truth。
Problem
.envをチャットで送り合う、更新時に再配布する、誰の値が最新か分からない、誤commitする。
Alternatives
Infisical、dotenvx、Bitwarden Secrets Manager、手動.env共有。
Comparison
2026-09-19時点でDoppler Developerは3ユーザー無料。今回の3人チームに一致する。Infisicalも有力だが責務が重なるため併用しない。
Decision / Why
Dopplerを採択。今回必要なのはSelf-hostではなく、3人が同じSecretを安全に共有する単純な運用であるため。

Benefits

  • .env実値を配布しない
  • 更新時にSecretの正本が1箇所
  • CLI、Service Token、Integrationを利用可能

Drawbacks

  • 外部SaaS依存
  • 権限設定とToken管理が必要
  • 障害時にSecret取得方法を考える必要

Setup

  1. Project / Environmentを作成
  2. 各メンバーがCLI login / setup
  3. Secretを登録
  4. 開発コマンドをDoppler経由で実行
  5. CIはService Token等で連携
# 例
doppler login
doppler setup
doppler run -- <development-command>

Team Rules

  • Secretの実値をRepository、Issue、PR、チャットへ貼らない
  • .env.exampleにはキー名と説明だけ置く
  • Secret変更はDoppler側を正とする
Review Trigger: 無料プラン条件、チーム人数、必要な権限制御が変わった場合。

5.12–5.14 Formatter / Linter / Git Hooks / Test Strategy

ADOPTEDTiming: Day 1 → MVPConfidence: High
Overview
人間がレビューする前に機械で落とせる問題を自動化し、テストは重要度に合わせて層を分ける。
Problem
レビューがformat指摘で埋まる、型エラーやbuild failureがmainへ入る、デモ導線の回帰が直前に見つかる。
Decision
Formatter / Linter / Type Check（TS時）/ Unit / Integration / 主要Flow E2Eを採択。Husky + lint-staged等はcommit前の軽量チェックに利用する。

Test Responsibility

  • Unit：プロダクト固有ロジック
  • Integration：API + DB等
  • E2E：デモで絶対壊したくない主要User Flow

Trade-offs

  • カバレッジ率を目的にしない
  • UI細部へ過剰なUnit Testを書かない
  • E2E本数を増やしすぎてCIを重くしない

Default CI candidate

Format Check
  ↓
Lint
  ↓
Type Check
  ↓
Unit Test
  ↓
Build
  ↓
(必要になったら Integration / E2E)

Team Rules

  • CI失敗のままMergeしない
  • バグ修正時は再現テストを追加できるか検討する
  • 主要デモFlowはMVP完成後にE2E化する

5.15–5.20 Figma / Google Docs / ADR / Mermaid / Editor config / Releases

ADOPTEDTiming: 必要箇所からConfidence: High
Overview
FigmaはUI / Flow、Google Docsは議論中の文章、GitHub /docsは確定仕様、ADRは重要な設計判断、MermaidはGit管理可能な図、Git Tag / Releasesは提出状態の固定に使う。
Problem
UI・議事録・確定仕様・技術判断・Release状態が同じ場所に混在すると、正本が不明になる。
Decision / Why
情報の種類ごとに正本を明確化しつつ、確定した技術文書はRepositoryへ寄せる。Figma Starterは無料で、FigJamも利用できる。学生はEducation対象となる可能性がある。

Role split

  • Figma / FigJam：User Flow / Wireframe / UI
  • Google Docs：議事録 / ブレスト / 発表原稿下書き
  • /docs：確定仕様 / Architecture / Data Model / Operations
  • ADR：重要な技術判断
  • Mermaid：構成図・Sequence等

Repository hygiene

  • .editorconfigで基本フォーマット差を削減
  • .vscodeは必要最小限の推薦設定のみ
  • Tag / ReleaseでMVP、RC、提出版を固定
ADR基準: 「別の選択をしたらシステム設計や重要なトレードオフが変わる」判断だけ記録する。小さなライブラリ追加ごとには書かない。

7. Rejected Alternatives

Jira REJECTED

良い点：高度なIssue Tracking、Workflow、Dashboard。

比較：GitHub Issues + Projects。

今回見送る理由：3人・3週間ではGitHubとの二重管理がコスト。コードと作業を同じ場所に置く。

再検討：規模拡大、複数チーム、複雑な承認フローが必要になった場合。

Confluence REJECTED

良い点：Wiki型の共同ドキュメント。

比較：GitHub /docs + Google Docs。

今回見送る理由：確定仕様をコードと同じPRで変更できる方が審査・保守の両面で説明しやすい。

Notion REJECTED

良い点：柔軟な情報整理。

今回見送る理由：Google Docs / GitHub Projects / /docsと責務が重なる。

Infisical REJECTED

良い点：Secret管理、Integrations、Self-host選択肢。

比較：Doppler。

今回見送る理由：良い製品だが責務が完全に重複。3人のSecret共有という今回の問題にはDopplerを1つだけ採用する。

dotenvx REJECTED

良い点：暗号化.envをGit管理可能。

今回見送る理由：復号鍵の共有管理が別途必要。Secret集中管理という目的にはDopplerの方が単純。

CODEOWNERS REJECTED

良い点：Pathごとにレビュー担当を自動指定。

今回見送る理由：3人ならIssueごとのOwner / Reviewer指定で十分。特定領域の責任が固定されたら再検討。

Dev Container REJECTED FOR NOW

良い点：IDE / runtime / packagesまで再現。

今回見送る理由：mise + Docker Composeでまず十分。解決できない環境差が発生してから導入する。

10. Environment

Local

各開発者PC。miseでRuntime / CLI、Docker ComposeでDB等、DopplerでSecretを揃える。

Preview

PR単位で利用可能なHostingなら導入。レビュー担当がブラウザから確認できる状態を目指す。

Production

mainからのみDeployする方針を基本候補とする。ローカルからの直接Production Deployは避ける。

Environment Variables

  • Secret実値：Doppler
  • 必要なKeyの一覧：.env.example
  • Application起動時：Env Validation
  • Clientへ露出してよい変数 / Server-only変数を明確に分離
Production direct operation: Production DBやSecretを手作業で変更する必要が出た場合は、理由と手順を記録し、通常フローにしない。

12. Daily Development Guide

  1. ReadyからIssueを選ぶ。
  2. Ownerを設定する。
  3. Acceptance Criteriaを再確認する。
  4. mainを更新しBranchを作る。
  5. 実装する。
  6. Local Test / Formatter / Linterを実行する。
  7. 意味のある単位でCommitする。
  8. PRを作成しIssueをリンクする。
  9. CIを通す。
  10. ReviewerがCode Reviewする。
  11. VerifyでAcceptance Criteriaを確認する。
  12. Squash Mergeする。
  13. IssueをClose / Doneにする。
  14. 次のReady Issueへ進む。
Daily sync: 必要なら5〜10分で「昨日 / 今日 / Blocker」のみ共有。設計議論は別枠へ切り出す。

13. CI / Review / Merge Rules

Required checks candidate

  • Format Check
  • Lint
  • Type Check（TS時）
  • Unit Test
  • Build
  • 必要になったらIntegration / E2E

Merge condition

  • mainへ直接pushしない
  • PR必須
  • CI成功
  • 原則1人以上Review
  • Acceptance Criteria確認
  • Squash Merge

Reviewの優先順位

Correctness → Security / Data loss → Architecture / Responsibility → Test → Readability → Style の順。Styleは可能な限りFormatter / Linterへ任せる。

CI失敗時

失敗原因を修正してからMergeする。CI自体が誤検知の場合は「なぜ無視できるか」を明確にし、恒常的なSkipルールにしない。

15. API Rules

この章は独立HTTP APIを採用した場合のみ適用する。Server Actions等を中心にする場合、OpenAPI / Brunoを無理に導入しない。

Contract

  • OpenAPIをSingle Source of Truth候補にする
  • Request Validation
  • Responseの型 / Schema
  • Status Code
  • Error Contract

Operational rules

  • Authentication / Authorization
  • Timeout
  • 有限Retry
  • Rate Limit対応
  • Versioningは必要性が出た時のみ

Error Contract

Endpointごとに {error:"error"} 等の独自形式を乱立させない。RFC 9457 Problem Details等も参考に、統一されたError構造を設計する。

Bruno

独立API採用時は、CollectionをRepository付近へ置き、API変更と同じPRで更新できる形を候補とする。BrunoはGitを使ったCollection共同管理を公式にサポートする。

18. Decision Rules

新技術を提案するときは、以下へ答えられない限り「採用」へ進めない。

  1. 何の問題を解決するのか。
  2. 現状の方法ではなぜ不足するのか。
  3. 代替手段は何か。
  4. 既存ツールと責務が重複していないか。
  5. 導入コストは何か。
  6. 学習コストは何か。
  7. デバッグコストは何か。
  8. 3週間で元が取れるか。
  9. 審査員から「なぜ？」と聞かれてチーム自身が答えられるか。
  10. ADRとして残すほど重要な判断か。
ADRを書く目安: 別案を選ぶとArchitecture、データモデル、運用、重要なトレードオフが変わる決定。
